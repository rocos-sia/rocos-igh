# ROCOS IgH 版本维护

以仓库根目录 `VERSION` 为唯一版本来源，允许 `X.Y.Z` 和 `X.Y.Z-rc.N`；数字不带前导零，N 从 1 开始。CMake 的 `ROCOS_IGH_VERSION` 保留完整版本，`PROJECT_VERSION` 仅使用数字核心。不要修改 PDO YAML 的格式版本或历史设计文档中的版本示例。

本技能通过根目录 `AGENTS.md` 接入项目工作流。普通编辑不递增版本；用户要求提交时，将版本修改与本次改动放在同一提交中，不另造一个版本提交。请求使用本技能不等于要求立即提交或推送。

## 判断兼容性与渠道

先检查 `git status --short`、暂存及未暂存差异、HEAD 中的版本、相关历史和 `git tag --list 'v*'`。以实际将提交的文件判断本次变化，同时评估当前发布周期累计的变化，不能仅凭提交标题分类。不要将无关用户改动纳入提交。

| 级别 | 本项目判断依据 |
| --- | --- |
| patch | 向后兼容的修复、性能改进，或不改变使用契约的文档、测试、构建维护、配置示例修改 |
| minor | 向后兼容的新功能、可选配置、公共 API 扩展 |
| major | 破坏兼容性的 API、共享内存 ABI、IPC 命名或语义变化，移除/重命名配置或 CLI 参数，改变导致旧客户端或旧配置无法继续使用的默认行为 |

重点检查 `EcatBus`/`Slave`/`PdVar` 的布局和数组上限、旧别名、主站 ID 隔离、PDO 读写契约及周期行为。即使当前主版本为 0，也采用上述项目约定：破坏兼容性提升 major。混合改动取最高级别。

渠道与级别分开确定：

- “内部测试”“rc”表示内部渠道，但仍按兼容性选择目标数字核心。
- “发布 patch/minor/major”或明确要求“patch/minor/major 更新”表示正式渠道；“发布正式版”表示正式渠道并自动评估级别。
- “提交”“更新版本”没有明确渠道时，先完成改动审查和可独立执行的验证，再询问：“本次为〈兼容性判断及理由〉，选择内部测试〈候选 rc 版本〉，还是正式〈级别及候选版本〉？”说明这是根目录 `AGENTS.md` 与本技能要求的渠道确认，并链接规则。等待回答期间不写最终版本、不创建提交或标签。
- 用户在当前任务中已经明确渠道或给出持续适用指令时，直接沿用。用户指定级别低于实际兼容性需求时，说明冲突并询问；不要默默将破坏性变更当作 patch 发布，也不要擅自改成另一个正式级别。用户指定更高级别可遵从。

## 计算版本

区分 HEAD 中已经提交的版本与工作区中尚未提交的候选版本。重试同一次提交时复用已确认的候选，不因失败或重复运行再次加一。

1. 找出当前分支可达的最近正式发布基线，检查 `vX.Y.Z` 标签及其提交中的 `VERSION` 是否一致；多条历史汇合时按数字元组比较，不能按字符串排序。检查所有本地标签以防重名，但不要把其他分支的发布自动视为当前分支基线。
2. 尚无正式标签时，使用历史中最近的无后缀 `VERSION` 作为初始化基线；旧历史无此文件时读取对应提交中 CMake 的项目版本。本仓库建立机制时的基线为 `0.1.0`，不因此补打发布标签。若历史不完整，先查明基线再计算，不凭空假定已经发布。
3. 从正式基线按累计最高级别计算目标核心：patch 为 `X.Y.(Z+1)`，minor 为 `X.(Y+1).0`，major 为 `(X+1).0.0`。保留用户已确认且不低于兼容性要求的更高目标；不把现有 rc 的核心向下调。
4. 内部渠道：当前 HEAD 已是同一目标核心的 rc 时，N 加一；从正式版开始或目标核心升高时，从 `-rc.1` 开始。新功能或破坏性变化可能使 patch 的 rc 转入 minor/major 的 rc。
5. 正式渠道：当前 rc 的核心已满足本轮累计兼容性需求时，去掉 `-rc.N` 即发布该核心，不再额外提升一次。需求变高时，使用相应更高核心。当前 HEAD 是正式版时按第 3 步提升。
6. 明确指定的完整版本也须检查格式、兼容性和递增关系。每个新提交的版本必须高于各父提交版本（按语义化版本比较），正式版高于同核心的 rc；拒绝重复或倒退。冲突时说明原因并请求调整。

以已发布 `0.1.0` 为基线的示例：

| 已提交版本 | 累计改动 / 本次渠道 | 最终版本 | 标签 |
| --- | --- | --- | --- |
| `0.1.0` | 修复 / 内部 | `0.1.1-rc.1` | 无 |
| `0.1.1-rc.1` | 继续修复 / 内部 | `0.1.1-rc.2` | 无 |
| `0.1.1-rc.2` | 修复验证完成 / 正式 patch | `0.1.1` | `v0.1.1` |
| `0.1.1-rc.2` | 新增兼容功能 / 内部 | `0.2.0-rc.1` | 无 |
| `0.2.0-rc.3` | 兼容功能验证完成 / 正式 minor | `0.2.0` | `v0.2.0` |
| `0.1.0` | 共享内存 ABI 不兼容 / 正式 major | `1.0.0` | `v1.0.0` |

## 更新、提交与标签

1. 渠道和候选版本确定后，修改 `VERSION`，保持单行并以换行结尾。只更新确实跟踪当前版本的其他元数据，不批量替换历史版本文字。
2. 按根目录 `AGENTS.md` 执行与改动相关的验证。修改版本后至少运行无硬件 CMake 配置，确认完整版本有效且数字核心正确；涉及代码时继续执行相应构建和测试，不默认执行硬件集成测试。
3. 精确暂存本次文件与 `VERSION`，检查 `git diff --cached --check`、暂存差异及暂存版本。确认版本变化与其他改动在同一提交中，不覆盖无关暂存内容。记录旧版、新版、渠道、级别和依据供提交结果说明。
4. 正式发布在提交前检查目标 `vX.Y.Z` 不存在；若已经存在于其他提交，不覆盖、不删除，先解决冲突。用户已明确正式发布，即授权创建对应的本地标签，无需再次询问。
5. 创建已获授权的 Git 提交。提交成功后读取该提交中的 `VERSION` 并核对；内部版本不创建发布标签。正式版本使用附注标签，例如 `git tag -a v0.1.1 <新提交哈希> -m 'Release v0.1.1'`，标签必须指向包含该版本的提交。校验 `git rev-parse 'v0.1.1^{commit}'` 与目标提交一致。
6. 标签失败时报告“提交成功、标签未完成”，修复后仅重试标签，不额外升版或重复提交。同名标签已正确指向目标提交则视为该步完成。未经用户要求不 push 提交或标签。

创建合并提交时也要在提交前纳入版本更新并与各父提交比较，可用 `--no-commit` 准备合并；快进不产生新提交，不另升版。rebase/cherry-pick 等重放先解决版本冲突与递增关系；不要擅自移动已发布标签。amend 仅在用户要求时执行，同一尚未发布提交的修正可复用其候选版本，内容改变兼容性级别则重新计算；已经打正式标签的提交通过新提交发布修复。

最后报告旧版 → 新版、兼容性依据、验证结果、提交哈希以及实际创建的标签；未完成的步骤如实说明。
